# Application Life Cycle Management

#### 1. Core Focus & Exam Domain

* **Lecture Topic:** Application Lifecycle Management (ALM) Environment Topology, Solution Management (Unmanaged vs. Managed), and CI/CD Automation with GitHub Actions
* **Relevant PL-400 Domain:** Create a technical design (Implement Application Lifecycle Management [ALM] / Validate requirements and design technical architecture) & Extend the platform (Configure and manage solution components)

---

#### 2. Features & Technical Capabilities Taught

* **Application Lifecycle Management (ALM) Environment Topology:**
* **What it does:** Enforces environmental separation across software delivery phases to isolate active customizations from production operations. Standard topology consists of:
* *Development / Test Environment (Unmanaged):* Workspace where customizations, schema changes, and code assets are introduced and unit tested.
* *Build Environment (Ephemeral/Staging):* Dedicated environment used strictly by automated build pipelines to import unmanaged assets, compile/validate dependencies, and generate a standardized managed solution artifact.
* *Production Environment (Managed):* Stable, live operational runtime for business users hosting strictly managed solutions.


* **When/Why to use it:** Protects business continuity and prevents direct customizations in production ("cowboy coding"), ensuring that regressions, dependency breaks, and configuration errors are caught early in the deployment pipeline.
* **Key Constraints / Limits:** Production environments should block direct schema customization and unmanaged imports. Modifying components directly in downstream environments creates unmanaged layers that block future managed solution upgrades.


* **Solution Packaging Strategy (Unmanaged vs. Managed Solutions):**
* **Unmanaged Solutions:**
* *What it does:* Open container representing the source of truth for solution components. Components can be freely added, modified, or deleted. Deleting an unmanaged solution wrapper removes only the container metadata, leaving all customized components in the environment.
* *When/Why to use it:* Restricted exclusively to development environments and source control synchronization branches.


* **Managed Solutions:**
* *What it does:* Sealed, compiled distribution package where components are locked down based on managed properties. Deleting a managed solution cleanly removes the solution container and all its associated components and stored data.
* *When/Why to use it:* Mandatory deployment format for downstream testing, user acceptance testing (UAT), pre-production, and production environments.
* *Key Constraints / Limits:* Managed solutions cannot be directly edited in place (unless customized via unmanaged extension layers, which is an ALM anti-pattern). Component lifecycle updates require formal solution upgrades or patches.




* **CI/CD Automation via GitHub Actions (Source Control & Continuous Delivery):**
* **What it does:** Replaces manual export/import operations with declarative workflow pipelines (`.github/workflows/*.yml`) using Power Platform Actions for GitHub:
* Automatically exports and unpacks unmanaged solutions from development into a Git repository.
* Merges pull request (PR) changes into the `main` branch.
* Provisions an ephemeral build environment or leverages a dedicated build instance to convert unpacked source files into a compiled managed solution.
* Deploys the generated managed solution package automatically into target production/downstream environments.


* **When/Why to use it:** Eliminates human deployment errors, provides deterministic commit-based versioning, enforces automated code reviews before merging, and provides an audit trail of changes.
* **Key Constraints / Limits:** Requires configuring Entra ID Application Users (Service Principals) with non-interactive client secrets or federated workload identities in target Power Platform environments.

#### 3. Developer & Configuration Touchpoints

* **Developer Artifacts:**
* **Source Control Repository (GitHub):**
* Git branching model (feature branches targeting `main`).
* Repository tree containing unpacked solution XML schemas, web resources, plugins, and metadata manifests (`Solution.xml`, `Customizations.xml`).


* **GitHub Actions Workflow Pipelines:**
* Action references: `microsoft/powerplatform-actions` (e.g., `export-solution`, `unpack-solution`, `pack-solution`, `import-solution`).


* **Target Environment Solution Manifests:**
* Exported Unmanaged Solution `.zip` (intermediate artifact in dev).
* Compiled Managed Solution `.zip` (generated by the build pipeline).




* **Security & Permissions Required:**
* **Microsoft Entra ID (Azure AD):** App Registration (Service Principal) configured with API permissions (`Dynamics CRM` $\rightarrow$ `user_impersonation`) or Federated Credentials for GitHub Actions.
* **Power Platform Environment:** Application User associated with the Service Principal and granted the **System Administrator** security role across Dev, Build, and Production environments to execute solution import/export pipelines without interactive user prompts.
* **GitHub Secrets:** Stored repository secrets for `POWERPLATFORM_CLIENT_ID`, `POWERPLATFORM_TENANT_ID`, `POWERPLATFORM_CLIENT_SECRET`, and environment URLs (`DEV_URL`, `BUILD_URL`, `PROD_URL`).

#### 4. Hands-On Lab Candidates (Seed Ideas)

* **Logistics Scenario:** Configure a 3-tier ALM pipeline where an unmanaged dispatch routing solution is exported from a sandbox environment, unpacked into a GitHub repo, validated through an automated build pipeline that converts it into a managed package, and deployed into a production fleet environment.
* **Healthcare Scenario:** Implement a GitHub Actions continuous deployment workflow for an emergency triage solution that prevents clinical downtime by automatically compiling an unmanaged patient intake solution into a managed artifact and importing it into a locked-down hospital production tenant.
* **Professional Services Scenario:** Build an enterprise ALM release pipeline for a project billing solution that triggers upon pull request approval into the `main` branch, provisioning a temporary build environment to generate a managed solution and asserting that downstream imports into production enforce managed immutability.
