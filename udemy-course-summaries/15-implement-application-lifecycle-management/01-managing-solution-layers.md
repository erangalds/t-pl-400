# Managing Solution Layers

#### 1. Core Focus & Exam Domain

* **Lecture Topic:** Dataverse Solution Layering Architecture, Conflict Resolution, and Unmanaged Layer Removal
* **Relevant PL-400 Domain:** Create a technical design (Implement Application Lifecycle Management [ALM]) & Extend the platform (Configure and manage solution components)

---

#### 2. Features & Technical Capabilities Taught

* **Solution Packaging Models (Unmanaged vs. Managed Foundations):**
* **Unmanaged Solutions:**
* *What it does:* Serves as the mutable development container where components (tables, columns, forms, flows, web resources) are authored, edited, or deleted.
* *When/Why to use it:* Exclusively in sandbox and development environments.


* **Managed Solutions:**
* *What it does:* Compiled, sealed deployment units generated by exporting an unmanaged solution and setting the package type to *Managed*.
* *When/Why to use it:* Standard deployment artifact for non-development downstream environments (User Acceptance Testing [UAT], System Integration Testing [SIT], Pre-Production, and Production).




* **Solution Layering Stack & Hierarchy:**
* **What it does:** Organizes customizations into an evaluation stack calculated from bottom to top:
1. *System Solution (Base Layer):* The underlying root platform schema provided by Microsoft Dataverse at the very bottom.
2. *Managed Solution Layers (Intermediate Stack):* Managed packages installed sequentially over the system layer.
3. *Unmanaged Solution Layer (Active Customization Top Layer):* Any direct customizations made in the current environment float to the absolute top of the stack as an **Active** layer.


* **Conflict Resolution Rules (Winning Customizations):**
* *System vs. Managed:* Managed solutions take precedence over the System Solution.
* *Managed vs. Managed:* When multiple managed solutions modify the same component without discrete merge behavior, the **last installed managed solution wins** ("top-wins" principle), unless specific component-type merge logic applies.
* *Unmanaged vs. All:* Any unmanaged/active customization sitting at the top of the stack **always wins and overrides all underlying managed and system layers**, potentially masking intentional updates delivered by subsequent managed solution upgrades.


* **Component Merge Logic:**
* Certain component types merge non-conflicting properties (e.g., localized labels, security role row privileges, and attribute picklist/choice options) rather than completely replacing the underlying definition.




* **Solution Layer Inspection & Unmanaged Layer Remediation:**
* **What it does:** Allows administrators and developers to inspect component heritage via **Advanced $\rightarrow$ See solution layers** from Maker Studio or the classic interface.
* **Inspection Blades & Tabs:**
* *Updated Tab:* Displays properties specifically altered or added by the selected solution layer (e.g., schema modifications, field attributes).
* *All Tab:* Details the entire property collection (both inherited/unchanged and modified).
* *Contextual Tabs:* Surfacing component-specific variations such as *Localized Labels* (multi-language string entries), *Row Privileges* (security role matrices), and *Attribute Picklist Values* (choice/optionset items).


* **Remove Active Customizations / Delete Unmanaged Layer:**
* *What it does:* Permanently deletes the unmanaged modification sitting at the top of the component stack, allowing the underlying managed solution layer to surface and regain active precedence.
* *Key Constraints / Limits (Exam Critical):* **Irreversible operation**. Once active customizations are deleted, they cannot be undone. Developers must ensure underlying managed packages contain the required baseline configuration before removing the active layer.

#### 3. Developer & Configuration Touchpoints

* **Developer & Administration Artifacts:**
* **Power Apps Maker Portal (`make.powerapps.com`):**
* Navigation: Open target Solution (or Default Solution) $\rightarrow$ Locate Component (e.g., Table, Security Role, Form, Web Resource) $\rightarrow$ Context Menu (`...`) $\rightarrow$ **Advanced** $\rightarrow$ **See solution layers**.
* Layer Remediation: Select top-level **Active** layer $\rightarrow$ Action Bar $\rightarrow$ **Remove active customizations**.


* **Solution Export Configuration:**
* Action: Export solution $\rightarrow$ Package Type toggle (`Managed` vs. `Unmanaged`).


* **Power Platform CLI (`pac` equivalent touchpoints):**
* `pac solution list`
* Automated detection/removal via ALM deployment pipeline tasks (e.g., `PowerPlatformImportSolution` with `StageAndUpgrade` or `ForceOverwrite` parameters).




* **Security & Permissions Required:**
* **System Role:** System Customizer or System Administrator role within the target Dataverse environment to view solution layers, export solutions, and purge active unmanaged customization layers.

#### 4. Hands-On Lab Candidates (Seed Ideas)

* **Logistics Scenario:** Diagnose why a recent managed solution update to a freight consignment form failed to display new carrier tracking fields in UAT by inspecting the form’s solution layers, discovering a blocking unmanaged layer created by manual testing edits, and executing **Remove active customizations** to restore the managed layout.
* **Healthcare Scenario:** Audit a clinic management system where custom `Patient Admission` security role privileges were accidentally modified in production, examining the *Row Privileges* tab within the security role solution layers to identify unmanaged overrides and safely revert to the approved compliance baseline.
* **Professional Services Scenario:** Investigate a deployment collision where two managed project accounting packages alter the same `Billing Milestone` choice column, reviewing the *Attribute Picklist Values* layer tab to determine how Dataverse merged the option values according to the installation sequence.
