# Adding Code to Our Plug-in 

#### 1. Core Focus & Exam Domain

* **Lecture Topic:** Dataverse Plug-in Execution Context, Target Extraction, and Entity Attribute Mutation
* **Relevant PL-400 Domain:** Extend the platform (Create a Dataverse plug-in / Manage execution context)

---

#### 2. Features & Technical Capabilities Taught

* **`IServiceProvider` Dependency Injection:**
* **What it does:** Service container passed directly into the `Execute(IServiceProvider serviceProvider)` entry point of an `IPlugin` implementation.
* **When/Why to use it:** Used to resolve runtime Dataverse platform services and execution interfaces (such as `IPluginExecutionContext`, `IOrganizationServiceFactory`, and `ITracingService`) via `serviceProvider.GetService(typeof(T))`.
* **Key Constraints / Limits:** Requires explicit casting (e.g., `(IPluginExecutionContext)serviceProvider.GetService(...)` or `serviceProvider.GetService(...) as IPluginExecutionContext`).


* **`IPluginExecutionContext` Interface:**
* **What it does:** Provides detailed contextual metadata regarding the runtime event triggering the plug-in execution.
* **Properties Exposed:**
* `Stage`: Identifies the numeric pipeline execution stage (e.g., Pre-validation [10], Pre-operation [20], Post-operation [40]).
* `ParentContext`: References the parent execution context if this operation was triggered by another plug-in or system event (detecting re-entrancy / nesting depth).
* `InputParameters`: A parameter collection containing the message request parameters payload.


* **When/Why to use it:** Essential for evaluating pipeline states, verifying trigger criteria, and extracting inbound/outbound record payloads.


* **`InputParameters["Target"]` Property:**
* **What it does:** Holds the primary data payload that triggered the platform message (e.g., `Create`, `Update`, `Delete`). For record operations, it contains the entity payload cast as `Entity`.
* **When/Why to use it:** Standard mechanism to read and alter field values submitted in the pipeline before they are committed to the database.
* **Key Constraints / Limits:**
* The `"Target"` key is used across most standard CRUD messages (`Create`, `Update`), but distinct messages use different keys (e.g., `RetrieveMultiple` uses `"Query"` in request parameters and `"BusinessEntityCollection"` / results in response output parameters).
* The `Target` entity in an `Update` message contains **only the attributes being modified** (dirty fields), not the full table row.




* **Pipeline Pre-Validation & Pre-Operation Attribute Alteration:**
* **What it does:** Reading and mutating attribute values within the `Target` entity during Stages 10 (Pre-validation) and 20 (Pre-operation) prior to the physical database transaction commit.
* **When/Why to use it:** Preferred when modifying or enriching attributes on the incoming record without incurring the overhead of issuing an additional `IOrganizationService.Update` call.
* **Key Constraints / Limits:** Direct mutations to `Target` attributes are automatically persisted to the database only during pre-operation/pre-validation stages. Mutations attempted in Post-operation (Stage 40) require explicit `IOrganizationService.Update()` service calls.


* **Late-Bound Entity Indexer Access & Schema Name Sensitivity:**
* **What it does:** Accesses table attributes using the generic `Entity` class indexer syntax: `entity["attribute_logical_name"]`.
* **When/Why to use it:** Used in late-bound development where early-bound entity classes (generated by `CrmSvcUtil` or `pac modelbuilder`) are not configured.
* **Key Constraints / Limits:**
* Attribute names must strictly match the **all-lowercase logical name** defined in the Dataverse schema (e.g., `address1_line3`), not display names or PascalCase column names.
* Accessing an attribute using incorrect casing or accessing a non-existent key throws a `KeyNotFoundException` if the field was not provided in the update payload.
* Requires explicit casting (e.g., `(string)entity["address1_line3"]`) because the indexer returns generic `object` types.




* **Exception Handling & Event Cancellation:**
* **What it does:** Aborts the current transaction and displays user-facing error dialogs via `InvalidPluginExecutionException`.
* **When/Why to use it:** Enforcing synchronous validation rules to rollback the database transaction and return meaningful business error messages.
* **Key Constraints / Limits:** Must use `InvalidPluginExecutionException` for user-friendly error surfacing; standard unhandled .NET exceptions (like `NotImplementedException`) surface as generic platform system fault errors.

#### 3. Developer & Configuration Touchpoints

* **Developer Artifacts:**
* C# Class Library (.NET Framework 4.6.2) project implementing `IPlugin`.
* Late-bound entity property extraction:
```csharp
public void Execute(IServiceProvider serviceProvider)
{
    IPluginExecutionContext context = (IPluginExecutionContext)serviceProvider.GetService(typeof(IPluginExecutionContext));

    if (context.InputParameters.Contains("Target") && context.InputParameters["Target"] is Entity)
    {
        Entity entity = (Entity)context.InputParameters["Target"];

        if (entity.Attributes.Contains("address1_line3"))
        {
            string addressLine3 = (string)entity["address1_line3"];
            entity["address1_line3"] = "The data was " + addressLine3;
        }
    }
}

```




* **Security & Permissions Required:**
* **Developer/Admin:** System Administrator or System Customizer role to register the compiled plug-in assembly and configure execution steps via the Plug-in Registration Tool.
* **Runtime Execution:** Plug-in execution context executes under the identity specified in the step configuration (`Calling User` or a designated `Run in User's Context` Service Account).

#### 4. Hands-On Lab Candidates (Seed Ideas)

* **Logistics Scenario:** Build a synchronous Pre-operation plug-in on the `Shipment` table that intercepts the `Target` payload on `Create`, extracts the delivery instruction column (`log_deliverynotes`), sanitizes the text, and prepends standardized facility dispatch codes before the row commits.
* **Healthcare Scenario:** Implement a Pre-validation plug-in on the `Patient Intake` table that reads the `insurance_policynumber` attribute from `InputParameters["Target"]` and throws an `InvalidPluginExecutionException` if the format fails mandatory insurer checksum rules.
* **Professional Services Scenario:** Create a Pre-operation plug-in for the `Project Billing` entity that extracts unbilled hours from the `Target` entity, casts the value into a decimal, and automatically sets a calculated markup attribute directly on the inbound target record before persistence.
