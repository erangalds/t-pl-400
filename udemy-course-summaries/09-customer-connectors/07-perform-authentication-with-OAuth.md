# Perform Authentication by using OAuth 

#### 1. Core Focus & Exam Domain

* **Lecture Topic:** Custom Connector Authentication Types (Basic, API Key, OAuth 2.0 with Microsoft Entra ID) and MSAL Authentication for Dataverse Web API
* **Relevant PL-400 Domain:** Develop integrations (Create and configure custom connectors / Authenticate to the Microsoft Power Platform / Query the Dataverse Web API)

---

#### 2. Features & Technical Capabilities Taught

* **Custom Connector Authentication Architecture:**
* **What it does:** Defines the security handshake and credential transmission mechanism configured on the **Security** tab of a Custom Connector to authenticate outgoing HTTP calls to the backend service.
* **Supported Types & Profiles:**
* *No Authentication:* Anonymous invocation; used for public open APIs or endpoints where auth is supplied as arbitrary query parameters.
* *Basic Authentication:* Sends username and password encoded in the standard HTTP `Authorization` header.
* *API Key:* Passes a shared token/secret either as an HTTP request header (e.g., `x-functions-key`) or as a query string parameter (e.g., `?code=...`).
* *OAuth 2.0:* Token-based identity delegation using standard grant types (notably Authorization Code grant), supporting identity providers such as Microsoft Entra ID (Azure AD), Google, Facebook, and custom generic OAuth 2.0 providers.


* **Key Constraints / Limits:**
* Basic Authentication must strictly be paired with **HTTPS/SSL**; sending credentials over plain HTTP transmits Base64-encoded plain text over the public network.
* API Key authentication uses a static shared secret; if the key is rotated on the backend, existing platform connections become invalid until re-authenticated.




* **Azure Functions Host & Function Key Authentication:**
* **What it does:** Provides built-in serverless endpoint authorization at the function host level:
* *Host Keys:* Scoped across all functions within the entire Function App container.
* *Function Keys:* Scoped strictly to an individual target function (e.g., the `default` key).


* **When/Why to use it:** Lightweight authorization mechanism matching the **API Key** authentication mode in Custom Connectors.
* **Key Constraints / Limits:** Keys can be passed as the `code` query parameter (`?code=<key>`) or via the `x-functions-key` request header. Altering or omitting the key causes immediate HTTP `401 Unauthorized` / `403 Forbidden` execution failures.


* **OAuth 2.0 Identity Provider & Microsoft Entra ID (Azure AD) App Registrations:**
* **What it does:** Secures both Azure Functions and Custom Connectors using centralized enterprise identity. The Function App acts as the resource server (configured via the **Authentication** blade with Microsoft Entra ID as the identity provider), while the Custom Connector acts as the OAuth client application.
* **Supported Account Types (Audience Targeting):**
* *Single Tenant:* Accounts in this organizational directory only (internal enterprise lines of business).
* *Multitenant:* Accounts in any organizational directory (essential for ISV / Software as a Service [SaaS] multi-customer solutions).
* *Personal Microsoft Accounts:* Consumer identities (Skype, Xbox, Outlook/Live/Hotmail).
* *Multitenant + Personal Accounts:* Hybrid enterprise and personal Microsoft accounts.


* **Connector Configuration Parameters:**
* `Client ID` (Application ID assigned by Entra ID).
* `Client Secret` (Generated under Certificates & Secrets).
* `Authorization / Login URL` and `Token URL`.
* `Resource URL` (e.g., target Function App App ID URI or Dataverse service root).
* `Redirect URI`: Automatically generated by the Custom Connector; must be copied and registered into the App Registration's Authentication Redirect URIs (supporting unique per-connector redirect URIs).




* **MSAL (Microsoft Authentication Library) vs. Deprecated ADAL:**
* **What it does:** The official, current .NET client library (`Microsoft.Identity.Client`) used in programmatic C# apps and daemon utilities to acquire OAuth 2.0 access tokens for calling protected endpoints (such as the Dataverse Web API).
* **Architectural Shift / Exam Rule:** **ADAL (Active Directory Authentication Library) is completely deprecated and unsupported** (support ended June 2022). All modern .NET integrations must use **MSAL**.
* **`PublicClientApplicationBuilder` Pattern:**
* `Create(clientId)`: Binds the application to its Entra ID Application ID.
* `.WithAuthority(authority)`: Specifies the identity provider instance, signing audience, and tenant ID (`[https://login.microsoftonline.com/](https://login.microsoftonline.com/){tenantId}`).
* `.WithRedirectUri(redirectUri)`: Overrides the default callback URI matching the registered client redirection.
* `.Build()`: Instantiates the `IPublicClientApplication` engine.
* Evaluates the target environment Dataverse Web API service root endpoint (retrieved via Power Apps session details / developer resources: `https://<org>.api.crm<region>[.dynamics.com/api/data/v9.2/](https://.dynamics.com/api/data/v9.2/)`) to acquire scoped access tokens.

#### 3. Developer & Configuration Touchpoints

* **Developer Artifacts:**
* **Custom Connector Security Tab Configuration:**
* Authentication Type: `OAuth 2.0`
* Identity Provider: `Azure Active Directory`
* Fields: `Client ID`, `Client Secret`, `Resource URL` (e.g., `https://<org>.crm.dynamics.com` or Function URI).
* Redirect URL: Copy the platform-generated unique URL and register under Entra ID App Registration $\rightarrow$ **Authentication** $\rightarrow$ **Web / Single-page application platform**.


* **Microsoft Entra ID (Azure Portal):**
* Navigate to **App Registrations** $\rightarrow$ **New Registration**.
* Configure Audience: Single-tenant vs. Multitenant.
* Generate Secret: **Certificates & secrets** $\rightarrow$ **New client secret**.
* API Permissions: Delegated permissions (e.g., `user_impersonation`).


* **C# / .NET MSAL Integration Pattern:**
* NuGet Package: `Microsoft.Identity.Client`


```csharp
using System;
using System.Threading.Tasks;
using Microsoft.Identity.Client;

public class DataverseAuthService
{
    public static async Task<string> AcquireAccessTokenAsync(
        string clientId, 
        string tenantId, 
        string redirectUri, 
        string dataverseOrgUrl)
    {
        // Scopes require the Dataverse environment root appended with .default or user_impersonation
        string[] scopes = new string[] { $"{dataverseOrgUrl}/.default" };
        string authority = $"https://login.microsoftonline.com/{tenantId}";

        IPublicClientApplication app = PublicClientApplicationBuilder.Create(clientId)
            .WithAuthority(authority)
            .WithRedirectUri(redirectUri)
            .Build();

        // Acquire token interactively or via device code / silent cache
        AuthenticationResult result = await app.AcquireTokenInteractive(scopes)
            .ExecuteAsync();

        return result.AccessToken;
    }
}

```




* **Security & Permissions Required:**
* **Azure Entra ID Permissions:** Cloud Application Administrator or Application Developer role to register apps, configure redirect URIs, and create client secrets.
* **Power Platform Environment:** System Administrator or System Customizer to configure custom connector security parameters and test connection authorizations.

#### 4. Hands-On Lab Candidates (Seed Ideas)

* **Logistics Scenario:** Replace an insecure URL-query-based function key on a custom freight-tracking connector with **API Key** security mapped to the `x-functions-key` request header, confirming that malformed or omitted headers return HTTP 401 unauthorized errors during flow execution.
* **Healthcare Scenario:** Secure a patient encounter REST endpoint in an Azure Function by enabling Microsoft Entra ID authentication and configuring a Custom Connector using **OAuth 2.0 (Single-Tenant)** with `user_impersonation` permissions so that only verified hospital staff accounts can invoke the service.
* **Professional Services Scenario:** Build an external C# console migration utility using **MSAL** (`PublicClientApplicationBuilder`) to authenticate against a Dataverse environment using a multitenant App Registration, extracting an OAuth 2.0 Bearer token to query the Dataverse Web API v9.2 endpoint.
