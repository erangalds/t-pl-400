**Background -**

Northwind Traders uses Microsoft Dynamics 365 Sales to manage its sales process. To better understand its customers, Northwind Traders invests in a team of researchers who gather data from multiple sources. The company stores the data it collects in a Microsoft Azure SQL Database. The company plans to use the data to enrich account records and make the sales team more effective.

---

**Current environment -**

**Environment -**

* The company has three Microsoft Power Platform environments with Dynamics 365 Sales installed. The environments are named development, test, and production.


* Each environment has an application user that can be used for integrations.


* The company must use solutions to perform all customization and configuration deployment.



**Data -**

* Researchers are responsible for creating account records.


* Researchers have permissions on the Account table to create records, read all records, and update records they own.


* A synchronous plug-in runs when an account record is created and could reassign the record to a different user.


* Users must access data as themselves to enforce security and audit changes.


* A column named new_dataid is added to the Account table. The column uniquely identifies which data it should receive.


* Researchers have researched only the top 20 percent of account records.



**Web API -**

* The company creates an Azure Function to run a RESTful .NET Web API.


* Data can be retrieved by placing a GET request to the URL https://dataservice-[ENVIRONMENTNAME].azurewebsites.net/enrich/[DATAID].


* [ENVIRONMENTNAME] is the name of the Microsoft Power Platform environment that requests the data.


* [DATAID] is the new_dataid column in the Account table.


* The Web API response will return a 200 response plus data if the DataId is found. Otherwise, a 404 response is returned.


* Developers plan to create a custom connector from the Web API to make it accessible from Microsoft Power Platform.

**Custom connector -**

**Process -**

The researchers want to avoid recreating the steps manually each time they create a flow to save time and avoid errors.

**C. custom connector**

---

### Detailed Breakdown & Architectural Reasoning

#### 1. Analyzing the Import Error & Missing Dependency

* **The Issue:** The scenario states that an error occurs when importing the solution containing the Power Automate flow into the test environment because a required component is missing.
* **The Flow's Architecture:**
* The cloud flow is built to update customer accounts with external enrichment data retrieved from a custom RESTful .NET Web API.
* To enable Power Automate to communicate with this Azure Function endpoint, developers built a **custom connector**.


* When a flow utilizes an operation defined in a custom connector, that flow establishes a strict schema dependency on the custom connector component within Dataverse solution management.
* If the flow is added to a solution and exported without including the referenced custom connector, attempting to import that solution into downstream environments (like Test) results in a **Missing Component / Dependency** error because the target environment does not have the custom connector definition.

---

#### 2. Why the Other Options Are Incorrect

* **A. connection:**
Standard connection instances (which bind credentials to a connector) are environment-specific runtime instances and cannot be packaged directly inside solutions. Instead, modern solutions use connection references, which merely point to a connection; the missing component causing the definition failure here is the underlying connector definition itself.
* **B. service endpoint:**
In Dataverse, service endpoints configure external integration targets (like Azure Service Bus or Event Hubs) for webhook or plug-in execution. They are not used by Power Automate flows to call REST APIs through custom connectors.
* **D. Account table:**
The case study notes that Dynamics 365 Sales is installed across all three environments (Development, Test, and Production). The `Account` table is an out-of-the-box standard entity that already exists natively in all target environments, so it will not trigger a missing component import block.

### Detailed Breakdown

#### 1. Why a Custom Process Action (with Custom Workflow Activity)?

* **The Requirement:**
*"The researchers require a process that repurposes a set of identical steps of parameterized Microsoft Dataverse queries from a Power Automate flow for use in other flows that have different parameters. The researchers want to avoid recreating the steps manually each time they create a flow to save time and avoid errors."*
* **Encapsulation via Custom Process Action:**
A **Custom Process Action** (formerly Custom Action in Dataverse/CRM) allows you to define a reusable custom API/operation directly in Dataverse.
* Unlike standard workflows, actions allow you to define typed **Input** and **Output parameters** (making it "parameterized").
* Within the action designer, you implement custom server-side business logic by invoking a **Custom Workflow Activity** (or plug-in step) that executes the parameterized queries against Dataverse.

---

### Step-by-Step Sequence

1. **Create a custom process action that uses a custom workflow activity to perform the Dataverse queries:**
Define the container process in Dataverse as an Action and attach the custom workflow activity that contains the query execution logic.
2. **Define the input parameters for the Dataverse queries:**
In the Action definition interface, configure the necessary input arguments (parameters) so that calling flows can pass dynamic criteria into the queries.
3. **Run the custom process action by using the Dataverse connector:**
In Power Automate, use the Dataverse connector's **"Perform an unbound action"** (or **"Perform a bound action"**) action to invoke the custom process action and supply the parameters from the flow.

---

### Why the Other Options are Incorrect

* **Create a real-time workflow that uses a custom workflow activity... / Run the real-time workflow by using the Dataverse connector:**
Real-time workflows do not natively accept custom parameterized input arguments from a Power Automate trigger in the same way custom actions do. Actions are specifically designed for parameterized caller invocations.
* **Create a custom process action that uses a plug-in to perform the Dataverse queries:**
While Custom APIs can bind to plug-ins, in the classic Process Action designer, the native workflow designer canvas incorporates **custom workflow activities** directly as process steps to define the core flow logic.

### The Business Requirement Explained

In the case study, researchers build multiple Power Automate cloud flows. Across these different flows, they repeatedly execute the same sequence of complex Dataverse queries. The only difference between each flow run is the specific filter values or query criteria—the **parameters**.

Rebuilding the same multi-step query logic inside every individual flow creates two major issues:

1. **Maintenance Overhead:** If the underlying schema, table structure, or query logic changes, every single flow has to be tracked down and edited manually.


2. **Duplication and Human Error:** Copy-pasting or manually recreating steps increases the likelihood of typos, mismatched filtering, or inconsistent results across teams.



The goal is **reusability and encapsulation**: build the query logic once inside Dataverse as a single, centralized callable unit, define input parameters for the dynamic values, and call that single unit from any Power Automate flow.

---

### Why the Architecture Fits: Custom Process Actions

In Microsoft Dataverse, operations can be encapsulated into several types of processes:

#### 1. Custom Process Action vs. Workflow

* **Workflows (Automated or Real-Time):** Workflows are primarily designed to be record-centric. They are tied to entity lifecycle events (such as Create, Update, or Delete) and do not support arbitrary, strongly typed input and output contracts exposed to external callers.


* **Custom Process Actions:** Actions are first-class web service operations in Dataverse. When you define an Action, Dataverse automatically exposes it as a custom endpoint on the Dataverse Web API. Most importantly, an Action allows you to define a formal **signature**:


* **Input Parameters:** Data passed *into* the action (such as query filter criteria, date ranges, or record IDs).


* **Output Parameters:** Data passed *back out* to the caller (such as query result collections or calculated aggregates).





#### 2. Why a Custom Workflow Activity inside the Action?

* An Action can include declarative steps (like update row, create row), but standard steps cannot execute arbitrary parameterized FetchXML/SDK queries and bundle the result into custom output parameters.


* To execute complex, dynamic Dataverse queries, developers compile C# code that inherits from `CodeActivity`—known as a **Custom Workflow Activity (CWA)**.


* Inside the Action’s process designer, you can add this Custom Workflow Activity as an execution step. The Action takes the inputs from the caller, passes them to the CWA, the CWA queries Dataverse, and returns the result.



---

### Step-by-Step Sequence Walkthrough

```text
+--------------------------------------------------------------------------------+
| Step 1: Create Custom Process Action with Custom Workflow Activity             |
|   - In Dataverse, create a new Process of category "Action".                   |
|   - Add a step invoking the Custom Workflow Activity containing query logic.   |
+--------------------------------------------------------------------------------+
                                       │
                                       ▼
+--------------------------------------------------------------------------------+
| Step 2: Define the Input Parameters                                            |
|   - Add formal arguments (e.g., QueryString, AccountType, MinDate) in Action UI|
|   - Map these inputs directly into the Custom Workflow Activity step.          |
+--------------------------------------------------------------------------------+
                                       │
                                       ▼
+--------------------------------------------------------------------------------+
| Step 3: Run the Action in Power Automate via Dataverse Connector               |
|   - In Flow, select "Perform an unbound action" or "Perform a bound action".   |
|   - Choose the custom action and pass dynamic parameters into the inputs.      |
+--------------------------------------------------------------------------------+

```

1. **Create a custom process action that uses a custom workflow activity to perform the Dataverse queries:**
You define the reusable container in the Dataverse process builder and embed the compiled query logic (the CWA) into the process pipeline.


2. **Define the input parameters for the Dataverse queries:**
You configure the formal contract in the action designer so that callers know what data must be provided to run the queries.


3. **Run the custom process action by using the Dataverse connector:**
In Power Automate, makers can add the native Dataverse action **Perform an unbound action** (or **Perform a bound action**). Power Automate automatically reads the Action's metadata and dynamically renders form fields for the input parameters you defined in Step 2, allowing any researcher to call the logic cleanly and consistently.

The correct answer is **D. `new_dataid ne null**`.

### Detailed Breakdown

1. **Trigger Filter Syntax (OData in Dataverse Triggers):**
* The Microsoft Dataverse connector trigger in Power Automate (*When a row is added, modified or deleted*) includes a **Filter rows** (row filter) parameter.


* This field accepts an standard OData filter expression to prevent the flow from firing unless the specified condition is met.

```odata
new_dataid ne null

```





---

### Why the Other Options are Incorrect

* **A. `not contains(new_dataid, '')`:**

* `eq null` filters for rows where the `new_dataid` field is empty/null, which is the exact opposite of the requirement (*"Only account records that contain a DataId..."*).

* `DataId` is the business/logical concept described in the case study, but the actual column name defined in the Dataverse table is explicitly stated as **`new_dataid`**. OData filter expressions require the exact schema/logical column name.

## Q256

You need to configure the custom connector to incorporate the environment name and DataId in the Web API URL.

Which four actions should you perform in sequence? To answer, move the appropriate actions from the list of actions to the answer area and arrange them in the correct order.

*(NOTE: More than one order of answer choices is correct. You will receive credit for any of the correct orders you select.)*

#### Available Actions:

* Set the operation to dataservice.
* Create a policy template that uses the Route request template.
* Set the subdomain of the URL template to:
`dataservice-@connectionParameters('EnvironmentName')`
* Set the path of the URL template path to:
`enrich/@queryParameters('DataId')`
* Create a policy template that uses the Set host URL template.
* Set the operation to enrich.

Here is a simplified explanation of what the question is asking and how the solution works:

---

### The Problem in Simple Words

You have a Web API living on Azure, and its full address looks like this:


$$\text{https://dataservice-}[\textbf{ENVIRONMENTNAME}]\text{.azurewebsites.net/enrich/}[\textbf{DATAID}]$$

Notice there are two moving parts in that URL:

1. **`[ENVIRONMENTNAME]`** (e.g., `development`, `test`, or `production`).
2. **`[DATAID]`** (the specific ID of the record being looked up).

The exam requires you to build a **Custom Connector** without hardcoding those two values, so it automatically reaches the right server and looks up the right record.

---

### How Custom Connectors Handle This

In Power Platform Custom Connectors, there is a feature called **Policy Templates**. Think of policies as automatic "search-and-replace" rules that tweak the web address right before the request is sent.

To fix both parts of the URL, you need **two policies** (and each policy needs its specific setting configured, making **4 steps in total**):

---

### The 4 Steps (In Order)

#### Part 1: Fix the domain name (`[ENVIRONMENTNAME]`)

1. **Create a policy template that uses the Set host URL template.**
* *What this does:* Tells the connector: *"I want to customize the website domain/host."*


2. **Set the subdomain of the URL template to: `dataservice-@connectionParameters('EnvironmentName')**`
* *What this does:* Plugs the current environment's name into the prefix so it hits `dataservice-development`, `dataservice-test`, or `dataservice-production`.



#### Part 2: Fix the path (`[DATAID]`)

3. **Create a policy template that uses the Route request template.**
* *What this does:* Tells the connector: *"I want to customize the specific path/route at the end of the address."*


4. **Set the path of the URL template path to: `enrich/@queryParameters('DataId')**`
* *What this does:* Attaches the record's ID to the end of the `/enrich/` path so it fetches data for the right record.



---

### Why the Other Options are Distractors

* **"Set the operation to dataservice"** / **"Set the operation to enrich"**:
* These are bogus options. An "operation" in a connector is the actual action name (like `GetCandidate` or `EnrichAccount`), not random URL fragments.
